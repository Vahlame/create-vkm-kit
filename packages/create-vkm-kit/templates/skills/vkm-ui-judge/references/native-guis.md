## Route B — Flutter (native)

Flutter ships deterministic UI-quality checks INSIDE `flutter_test` — no browser, no
extra dependency. Generate this test into the project (adjust the entry widget), run it,
fix, re-run. It is the same measure → fix → re-measure loop as the web route, with the
framework's own gates as the measurement:

```dart
// test/ui_judge_test.dart — generated by vkm-ui-judge; delete when done or keep as a gate.
import 'package:flutter/material.dart';
import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/main.dart'; // ADJUST: the app's root widget import

void main() {
  for (final size in const [Size(360, 740), Size(768, 1024), Size(1440, 900)]) {
    for (final brightness in const [Brightness.light, Brightness.dark]) {
      testWidgets('a11y+layout at $size / $brightness', (tester) async {
        final handle = tester.ensureSemantics();
        tester.view.physicalSize = size;
        tester.view.devicePixelRatio = 1.0;
        addTearDown(tester.view.reset);

        await tester.pumpWidget(MediaQuery(
          data: MediaQueryData(platformBrightness: brightness),
          child: const MyApp(), // ADJUST
        ));
        await tester.pumpAndSettle();

        // Deterministic gates, straight from flutter_test:
        await expectLater(tester, meetsGuideline(textContrastGuideline));
        await expectLater(tester, meetsGuideline(androidTapTargetGuideline));
        await expectLater(tester, meetsGuideline(labeledTapTargetGuideline));
        handle.dispose();
      });
    }
  }
}
```

Run with `flutter test test/ui_judge_test.dart`. Failures name the exact widget and the
measured value (e.g. contrast 2.9 < 4.5) — quote those, fix the theme token or widget,
re-run. An overflowing layout additionally surfaces as the classic
`A RenderFlex overflowed by N pixels` exception during `pumpWidget` — treat any such
exception at any size×brightness as an `overflow` error finding.

Verify the guideline names against the project's Flutter version before writing the test
(`flutter_test` docs); if a guideline is missing in an old SDK, drop that line and say so.
For visual regressions beyond the gates, add `matchesGoldenFile` per context — goldens
ARE the before/after evidence. Flutter **Web** builds should use Route A instead
(`flutter run -d web-server`, then the Playwright audit against the served URL).

## Route C — other native GUIs

Qt/C++, GTK, WinForms/WPF/MAUI (C#/.NET), Tkinter/PySide (Python), Java Swing/Compose,
etc.: there is no universal driver, so the evidence is **real screenshots + platform
scanners**. Never judge from source alone; never claim a check ran when it did not.

1. Build and launch the app.
2. Capture screenshots at ≥2 window sizes (small ~400px wide, large ~1400px wide) × OS
   light AND dark theme (commands below). Resize the window before each capture
   (programmatically if the toolkit allows, manually otherwise — say which).
3. Read the screenshots (they are images — actually look at them) and judge against the
   fixed checklist below, citing coordinates/regions per finding.
4. Run the platform accessibility scanner if one exists (below) — it provides the
   computed-contrast rigor pixels alone cannot.
5. Fix by severity, re-capture the SAME contexts, and state the before/after delta.

## Capturing screenshots per platform

- **Windows**: PowerShell — focus the window, then
  `Add-Type -AssemblyName System.Windows.Forms; [System.Windows.Forms.SendKeys]::SendWait('%{PRTSC}')`
  or use `dotnet` toolkits' own capture; dark mode toggle:
  `Set-ItemProperty HKCU:\SOFTWARE\Microsoft\Windows\CurrentVersion\Themes\Personalize AppsUseLightTheme 0` (1 = light).
- **macOS**: `screencapture -l $(osascript -e 'tell app "AppName" to id of window 1') out.png`;
  dark mode: `osascript -e 'tell app "System Events" to tell appearance preferences to set dark mode to true'`.
- **Linux (X11/Wayland)**: `import -window <id> out.png` (ImageMagick) / `grim` +
  `swaymsg`; dark mode via the desktop's gsettings
  (`gsettings set org.gnome.desktop.interface color-scheme prefer-dark`).
- **Toolkit-native capture** (preferred when available, no OS theme juggling): Qt
  `QWidget::grab().save(...)`, .NET `RenderTargetBitmap`, Tkinter via `ImageGrab.grab(bbox)`,
  Compose `captureToImage()`. Wire it behind a debug flag or a tiny test harness.

## Judging pixels: the fixed checklist

Same defect classes as the web audit, judged on the captured images — one verdict line
per class per context, no essays:

| class          | what to look for in the pixels                                                    |
| -------------- | --------------------------------------------------------------------------------- |
| `invisible`    | text that vanished after the theme flip (compare light vs dark captures)          |
| `contrast`     | text plausibly under AA — flag for the scanner or a color-picker spot check       |
| `overflow`     | clipped/truncated text, controls cut by the window edge, scrollbars at small size |
| `tap-target`   | controls visibly smaller than ~44px at the small window size                      |
| `misalignment` | rows/columns that don't line up, uneven padding, off-center dialogs               |

## Platform accessibility scanners

Real computed-contrast checks where the OS provides them — run them when present, name
them in the report, and skip silently to pixel judgment where they don't exist:

- **Windows**: Accessibility Insights for Windows (axe-windows CLI) — automated checks
  incl. contrast on any UIA app (WinForms, WPF, MAUI, Win32/Qt).
- **macOS**: Xcode Accessibility Inspector audit on the running app.
- **Android**: Accessibility Scanner app, or `flutter_test` guidelines for Flutter.
- **Linux**: no mature scanner — pixel checklist + toolkit color values from the source.
